# 交易内核（Rust）

> 量化策略实际运行的内核是 Rust，体检页的实时数据层、OKX 下单与平仓规划也在 Rust。Swift 保留 UI 与持久化。

## 1. 边界怎么划的

| 归属 | 内容 | 为什么 |
|---|---|---|
| **Rust 纯计算**（`kernel/src/` 除 `live/`） | 指标库、表达式 DSL、回测引擎、绩效指标、仓位计算、**实盘信号决策**、期权簿算术（`implied` 隐含分布、`gravity` max pain）、OKX 账户文档解析 | 确定性计算。正确性与可复现性是第一位的，且这里是「回测与实盘必须一致」的地方 |
| **Rust 实时层**（`kernel/src/live/`） | 体检页读的全部实时连接：OKX 公有行情与只读私有账户推送、Deribit 波动率曲面、Binance 标记价、嘉信报价推送，以及没有推送的 REST 读数（四家期权持仓量、5 分钟持仓结构、条件单、时钟、Polymarket 预测市场价格——主题按系列或事件声明在 `live/polymarket.rs`，到期自动滚到下一期。纽约日期 7 天内（`UPCOMING_DAYS`）要结算的主题排在前面；按天提问的盘只显示最近一天；已过截止、等待结算的盘只计数，不当作预测显示）；平仓面板的单标的盘口（`live/book.rs`） | 同一个数只有一份实现：线上帧、录制帧、回测都走同一批纯函数 |
| **Rust 交易通道**（`kernel/src/trade/`） | OKX 下单、策略委托、撤单、改止损、预检、按腿设杠杆（内核自己签名 REST）；每张单的保证金模式与开仓前那条腿的杠杆（`margin` / `leg`）；交易路径的签名读取（挂单、按 clOrdId 查单、费率、持仓、余额与估值、账户配置、成交、资金费、杠杆）；平仓规划（价格来源、逐档预估、复核文字） | 发出去的请求体、复核给人看的请求体、测试钉住的请求体是同一个函数的输出 |
| **Swift**（`Sources/`） | SwiftUI 界面、菜单栏、交易行情 WebSocket、okx CLI 桥（只剩账单流水）、嘉信 `schwabctl` 桥、配置与台账持久化、异步编排 | 平台 I/O 与界面 |

**签名 REST 只有一个出口，清单封闭**：所有签名 REST 请求——App 的下单与读取、实时层的条件单轮询——都经由进程唯一的 `trade::shared()` 客户端；能发的只有 `trade::wire::Action` 列出的七种动作，能读的只有 `trade::reads::Read` 列出的几种读取，每条路由都在 `trade::route::Route` 里，没有一个参数能指定任意路径。实时层自己只签 WebSocket 登录，私有频道只订阅 `positions` / `account`。密钥只在签名时从 okx CLI 的 `config.toml` 读，不另存、不写日志，`Debug` 打印不出任何一段。

### 1.0 实时层的形状（2026-09-24）

- **一个任务独占全部状态**。连接只转发收到的帧；解码、合并、所有派生数都在这个任务里按到达顺序算，没有锁，没有竞争。
- **每次更新重新发布一份带序号的快照（JSON）**。页面可见时 Swift 每帧（16 ms）调 `ms_live_snapshot(since)`，没变化时拿到 NULL，只花一次锁；窗口被遮挡、最小化或切到别的 Space 超过半秒，降到每秒一次，照常记事件日志、跟随 REST 兜底，但不重绘，重新可见时立刻发布最新一份。
- **每个数带交易所自己的时间戳**，界面按本机与交易所的时钟偏差（连测 6 次取往返最短）校正后显示毫秒级年龄。本机测得的时间（帧到达、轮询返回）在状态里是 `LocalMs` 类型，进快照只能经 `to_server` 换到交易所时钟——漏换是编译错误，不是随本机时钟漂移而错的年龄。
- **每个源在 `Feed::cadence` 声明自己的节奏**：轮询器按它睡眠，年龄超过 3 个节奏变黄（`Feed::stale_after_ms`，随快照发给界面）。socket 帧和成功返回的轮询走同一个 `note_frame` 记新鲜度，所以「多久前」对每个源是同一个意思。
- **风险按腿算，不按合约算**（2026-10-07）。同一合约可以同时持有多空两条腿（OKX 双向持仓模式），`risk.positions` 列出该合约上的每一条腿，各带自己的强平价、缓冲和强平概率。敞口按多、空分别累计（`gravity::Exposure`）：价格风险看净额；保证金、以及一条腿被强平后剩下的裸仓，看总额。条件单只归到它能平掉的那条腿，条件是同合约、同腿、方向为平仓方向（`WorkingOrder::closes`；「多卖空买」只在 `wire::Side::closing` 写一处）。不平任何腿的单（开仓或加仓触发）单独列在 `unattachedOrders`，不当作保护显示。
- **几家同时断就是本机网络**（2026-10-07）。每个源在 `Feed::operator` 声明它连的是哪一家；同时有 `NETWORK_OUTAGE_OPERATORS`（3）家以上「所有在跑的源都只剩失败」时，快照给出 `network`，写明连不上和还连得上的各是哪几家，事件日志在开始和结束时各记一行，页面用一条结论替代这几家的逐源告警。「只剩失败」的意思是：最近一次报告的是失败，且之后没收到过数据。重连中间的那次尝试也算失败；主动关掉的源不算。
- **预测市场每一档对应的 ETH**（2026-10-07）。测量写在 `Scripts/event-reactions.py`，结果写进 `kernel/data/event_reactions.json`，内核编译时嵌入，由 `live/reactions.rs` 按当前盘口换算到每一档。
  - 有结算历史的主题按「超预期幅度」回归。比如核心 CPI 和议息：从 Kalshi 阶梯盘公布前 5 分钟的报价还原当时的预期，把「实际 − 预期」对 ETH 公布后 1 小时、24 小时的涨跌做回归。当前每一档的超预期幅度，是相对卡片上各档按概率加权的期望值来算的。
  - 没有结算历史的主题（停火破裂、达成协议、打沙特设施等）走油价链：2026 年同类事件当天布伦特的超额涨跌，乘以 ETH 对布伦特的日 β。这类结果标明「推算」。
  - 只用斜率、不用截距：截距是样本期整体的涨势，不是事件本身的影响。
  - 斜率不到 2 倍标准误的窗口不给概率，显示「无关」。
  - 每个上卡片的主题都必须有测量，`every_declared_topic_has_a_measurement` 盯着这一点。
- **离线模式**：`ms_live_ingest` 把录制的帧送进与线上完全相同的解析路径，整条管线可测（`LiveKernelGoldenTests`）。
- **网络底线是实测出来的**，不是代码能改的：这台机器所有交易所流量走公司 VPN，单向 150–400 ms；高频流（Binance 期货 `bookTicker` 每秒约 65 帧）单独跑也迟到 1.6 s，并拖累同机其它流。所以只订阅小频道（Deribit 用整曲面一帧/秒的 `markprice.options`，而不是 26 个逐合约 ticker），并对每个连接只并发抢连 IPv4（IPv6 在这台机器上是黑洞，系统先试它会白等约 10 s）。

### 1.0.1 交易通道与盘口（2026-09-25）

May 的决定：「交易相关都走内核」「内核直接签名下单」，平仓面板要有最优价格和同向 / 对手第 N 档。实现与实测：

- **结果只有五种，且互斥**（`trade::Reply`）：`accepted`（交易所给了 ordId/algoId）、`rejected`（交易所自己的拒绝，带 sCode）、`notDelivered`（交易所确定没有处理：连接都没建立、一个字节没发出，或者被 OKX 限频挡回——限频在网关读请求之前就拦下，官方 CLI 也按「退避后重试」处理 50011/50061）、`unconfirmed`（发出去了但没有裁决——可能已成交，只能按 clOrdId 去查）、`refused`（在本机就拦下：实盘未解锁、密钥环境不对、订单写法交易所读不了）。超时、5xx、回复读一半断了、回复成功但没有 id，以及 OKX 自己的服务端错误码 `50001`/`50004`/`50013`/`50026`（OKX 对 50004 的说明是「不代表请求成功或失败」；`close-doctor` 实测在模拟盘查单时遇到过 50004），全部是 `unconfirmed`，绝不当成拒绝，也绝不重发。runner 对三种失败各有去向：拒绝→策略停下；没送达→清掉「本根 K 线已处理」标记，下一次轮询重下；未确认→记为在途，按 clOrdId 查到结果为止，不重发。
- **实盘锁在内核里**：实盘动作在读密钥之前就被拒；demo key 发实盘、实盘 key 发 demo 也在网络之前拒（本地模拟服务器测试钉住：被拒时服务器一个请求都没收到）。
- **连接常热**：交易客户端是进程级单例，IPv4、keep-alive；平仓面板一打开就预热，一笔单只付一次往返（实测模拟盘撤单 250–470 ms，含 VPN）。
- **建连这一步也按「抢最快」来**：OKX 的域名解析出多个 IPv4 边缘节点，连接器默认按解析顺序逐个尝试，排在最前的节点慢或挂了，一批并发连接就一起超时（实测：`close-doctor` 首批 15 个并发连接全部 `client error (Connect): operation timed out`，约 1/12 次）。所以 REST 客户端（交易与轮询共用 `net::FastestFirst`）解析时并发抢连所有 IPv4，把先答的放第一个，记住这个顺序 60 秒，同一时刻只跑一次抢连。即便如此，建连阶段（请求一个字节都还没发出）的失败仍会重签名重试，最多 3 次。发出之后的失败一律不重试，归 `unconfirmed`。
- **不超 OKX 的限频**（`trade::route`）：客户端访问的每条 OKX 路由都声明在 `Route` 里，附官方限额（按 ccxt 的 OKX 定义核对，cost 1 = 每 2 秒 20 次；官方 CLI 自己的节流放得更宽，algo 列表给了每秒 20 次）；请求只能经由 `Target` 发出，而 `Target` 只能由 `Route` 构造，`Route::limit` 是没有默认分支的穷举 match——新加一条路由，不写限额就编译不过。进程内按「账户 × 路由」配速：每个请求从放行起占一个名额，直到回复到达、再过一个窗口才让出。OKX 按到达计数，而到达一定不晚于回复，所以这样排出的请求在 OKX 那边任意一个窗口里都不超限，与网络和冷连接握手多慢无关——本进程自己永远不会超限。按「放行时刻 + 300 ms 抖动」计数是不够的：冷启动时估值读取（每秒 1 次）第一个请求在冷连接上飞了约 0.8 s，第二个走热连接追上，三次启动三次 `50011`；改成按回复计数后三次启动零次（2026-09-25 实测）。跨进程仍可能撞上（实测：App 轮询挂单的同时 `close-doctor` 读同一实盘账户，12 个 algo 列表里有 4 个被回 `50011 Too Many Requests`，而 OKX 对 `orders-algo-pending` 的限额是每账户每 2 秒 20 次），所以 HTTP 429 或 50011/50061 会等满一个窗口后重签重发，与建连失败共用 3 次的额度，仍被限频就归 `notDelivered`——不是拒单，runner 不会因此停掉策略。读取不改变任何东西，所以服务端出错（5xx 与上面四个码）时也等一两秒再问，同样计入 3 次。哪条路由会改变账户只由 `Route::acts` 声明一处。每个回复都带 `retries`、第一次重发的原因 `retryReason`，以及排过队的请求数 `pacedRequests` 和其中最长的等待 `pacedMs`（一次调用的请求是并排等的，所以取最长而不是加总）；这些用文字写成 `note` 只由内核写一次，App 原样写进 engine-log（`trade: … 重发 N 次（首次原因：…）` / `N 个请求为不超 OKX 限频排队，最长等了 N ms`），实时层写进自己的事件。实时层的条件单轮询也走同一个 `trade::shared()` 客户端（`Read::Protection` 不带品种即整个账户，一个 `conditional,oco` 请求），所以全进程的签名请求共用一个配速器；它在交易客户端自己的 runtime 上执行，连接不会挂在实时层的 runtime 上、随实时层停止而断在下一笔订单底下。
- **签名 POST 已端到端验证**：`close-doctor` 在模拟盘撤一笔不存在的订单，OKX 答 `51400`（订单不存在）——请求被认证、被读懂；每种价格来源 × 有效方式的平仓单都过了模拟盘的 `order-precheck`。预检只收合约：现货一律答 `3 Operation not supported`（实测）。
- **盘口**：订阅 `books`（400 档，100 ms 增量）+ `bbo-tbt`（10 ms）+ `tickers`。两者共用同一个 seqId 序列（实测：快照与其后第一条 bbo-tbt 的 seqId 相同），所以严格按序合并：增量的 `prevSeqId` 必须接上本地序号（心跳 seq==prev、维护重置 seq<prev 也都是「接上」），接不上即丢帧，断开重订阅从新快照重建，并计入 `resyncs` 由 App 记日志；比盘口新的 bbo 覆盖第一档并删掉盘口里所有比它更优的档（那些已被吃掉或撤掉）；合并后买一 ≥ 卖一视为丢帧。价格按十进制文本解析成整数（10⁻¹⁸），不用浮点做键。随机模型对拍：200 轮 × 300 帧，合并结果与真实盘口逐档一致。OKX 的 checksum 在这个频道恒为 0，不能用。l2-tbt 需要 VIP4，账户是 VIP1。
- **价格来源照 Binance 的 `priceMatch`**：对手价第 N 档（卖出=买 N，立即吃掉 1…N 档）、同向价第 N 档（卖出=卖 N，排队）、中间价（向对自己有利的一侧取整）、最新成交价、自定义（同样向有利侧取整）。OKX 没有服务端 BBO，所以在内核里按「面板上画的那份盘口」解析，复核冻结这份价格并写明它来自哪个 seq；复核后盘口再动，界面实时显示漂移，确认发送的仍是复核时的价格，复核超过 60 秒必须重新复核。
- **预估逐档走盘口**：立即成交量、均价、吃几档、最差价、相对中间价的滑点、挂单余量、IOC 撤销量、FOK 不足整单撤销、超出可见档位的市价量；手续费按合约自己的费率组（现货各组 taker 从 0.08% 到 0.32% 不等，实测，所以不按品种族一刀切），期权按「名义 × 费率」与「权利金 12.5%」取小；盈亏按合约条款（线性、反向、期权权利金、股票），现货余额没有成本价就不估。金额文本由内核写一次（`money_text`），界面只显示。
- **能做什么由内核声明一次**（`trade::close::capabilities`，按交易所 × 品种族），界面只提供声明里有的，规划器拒绝其余并给出声明里的原因；Swift 测试遍历每个交易所 × 品种 × 方式 × 价格来源 × 有效方式，断言每张复核里的请求体与 `send` 实际会签名的请求体逐字节一致。
- **嘉信**：只有一档报价、没有挂单量（`sizesKnown: false`），预估按「报价全部成交」算并在复核里写明这是假设；只提供 GTC 限价、市价和止损，其余在边界上按名字拒绝。

### 1.0.2 账户读数：一份文档，按标记价实时重估（2026-10-08）

起因是 May 的问题：「为什么 MayStock 的数值总是和手机上实时看到的不一致」。逐项实测，原因不是一个而是一类——**同一个账户被几套读数各自按自己的时钟、口径和单位读，再各自显示**：

| # | 现象 | 原因（实测） |
|---|---|---|
| 1 | 浮动盈亏、权益离手机平均 $52 / $27，最多 $173（实盘 21.5 ETH 多单，10 分钟） | 交易循环 60 秒采一次权益、账户刷新 300 秒读一次持仓、体检页另有推送，三份读数各管各的屏幕 |
| 2 | 权益标 USDT，实际是美元 | `totalEq` 是 USD；按同一次推送里的 `eqUsd/eq` 折成 USDT，差的就是 USDT/USD 汇率（0.9993） |
| 3 | 「今日」永远对不上「今日盈亏」 | 只数账单里已实现的部分；手机是「权益 − 北京时间 0 点权益 − 期间净划入」，含浮动 |
| 4 | 涨跌幅对不上 | 用滚动 24 小时；OKX App 用北京时间 0 点。现在做成设置，默认 0 点 |
| 5 | 划转算进收益 | 期间转入转出没扣；自动赚币（subType 381，每小时一笔）却是收益，不能扣 |
| 6 | 「本周」从周六量起 | 起点采样离周一 0 点太远也照用；现在超出曲线自身的连续性容差（细区 300 秒、粗区 1800 秒）就标明「起点晚了 / 早了」 |
| 7 | 体检页说「OKX 标记价时间戳本身约晚 4 秒（09-23 实测）」 | 重测推翻：估值用的 `mark-price` 年龄 p50 157 ms、p90 228 ms、最长 340 ms（172 份账户文档）；体检页抽样 214 / 306 / 172 ms。说明已删，阈值改由内核给出（见下） |
| 8 | 嘉信权益与持股来自两次 `schwabctl account` | 一次读数读两遍，两半差一个子进程；且只按交易循环的 60 秒读 |

**做法：账户只有一份读数**。

- **实时层的账户部分常开**（`spawn_account`）：私有 socket 订 `positions` / `account`（`updateInterval: 2000`，事件即推、另每 2 秒一份快照）与 `orders`；业务 socket 订 `orders-algo` / `algo-advance`（在私有 socket 上订回 `60018`）；账户所在环境的 `mark-price`，只订持有的合约（模拟盘走 `wspap`，它的标记价与实盘不同）；每个持有合约的规格（`rest.okx.spec.<id>`）；挂单整读（推送一说有变就读，间隔不低于 800 ms，另 5 秒兜底）；划转（`bills type=1`，从新到旧翻页、不带 `begin`，最多 10 页、回溯 8 天；账户推送一说现金动了就读，另 30 秒兜底）。体检页的行情分析另开另关（`LiveConfig.analytics`）。
- **每条腿在自己的实时标记价上按平仓面板同一个公式重估**（`trade::terms::pnl`）：线性 `(mark − avg) × |pos| × ctVal × ctMult × 方向`。实测与交易所逐分对上：`maystock-e2e account` 在 REST 读数的标记价上复算实时文档的浮盈，Δ 0.0000（6–9 次对比）。收益率用交易所自己的分母，从推送里的 `upl / uplRatio` 还原。没有新标记价或规格未读到时沿用推送值，并写明原因。
- **权益按币种重估**：`eq_now = (eq − upl)_推送 + Σ 各腿 upl_now`，再按推送里的 `eqUsd/eq` 折美元；没法重估的币种原样保留并点名（`unmarked`）。
- **一份文档**：`ms_live_account(since)`，序号只在账户变了时前进；Swift 每 250 ms 取一次（`LiveAccountFeed`），`VenueBooks` 采纳后，每块屏幕和交易循环读的都是这一份（`AccountReading`）。各部分各带时间戳（权益、持仓、挂单、成交），一份新鲜的权益不替一份旧挂单作保。
- **兜底分三层，每层都标出来**：私有 socket 断开超过 20 秒（`PRIVATE_GRACE_MS`）→ 文档置 `fallbackNeeded` → App 每 10 秒经内核签名的 REST 读一次持仓与余额文档、交给内核（`rest.okx.positions` / `rest.okx.account`；`Renewal::RestFallback`，App 的循环按 `ms_live_rest_fallback_ms` 睡），解析路径与推送完全相同——这条兜底以前叫「CLI 兜底」，但早已不经过 okx CLI；连这份也旧过 `positionsStaleAfterMs`（宽限 + 一次兜底读）→ App 按轮询节奏另读一份 `AccountReading`。界面写明当前是哪一层。
- **区间收益与手机同口径**：`(当前权益 − 起点权益)` 折成计价币，减去起点之后的本金划转（subType 11/12）；自动赚币算收益；不认识的类型按划转扣除并点名。已实现部分（账单）放在提示里。权益以计价币（USDT）显示，曲线每个点记下当时的 `quoteUsd`。
- **嘉信**：一次 `schwabctl account` 同时给出权益与持股；有随行情变动的持仓时每 10 秒读一次，只有现金时每 60 秒（`AccountReading.pollInterval`），每次都是嘉信自己的估值，App 不在两次之间自己重估（那是第二份估值规则，盘前盘后怎么估值无法核实）。划转经 `schwabctl transfers`（9 种资金进出类型各一个请求），持有数量一变就重读，否则一分钟一次。

**年龄与「变黄」只有一条规则**：每个带时间戳的值都带上它自己的过期阈值（`staleAfterMs`），等于更新它的那个时钟的 3 倍（`STALE_AFTER`）。时钟在 `live::Renewal` 声明一处：各源的帧（`Feed::cadence`），加上源内部更慢的时钟——这些是实测或文档给的，2026-10-08 在活跃行情下连测 150 秒：

| 时钟 | 间隔 | 依据 |
|---|---|---|
| OKX `mark-price` | 动时 200 ms，不动时 10 s | 实测中位 202 ms；静默心跳按文档 |
| OKX `funding-rate` | 30–90 s | 实测 58–72 s；推送自带的 `ts` 到达时可能已有 50 s |
| OKX `open-interest` | 只在变化时推 | 实测中位 6 s、最长 16 s（原阈值 15 s 会误报） |
| 5 分钟统计桶 | 300 s | 时间戳是桶的起点，正常年龄每轮都超过 10 分钟（原阈值 7 分钟会误报） |
| REST 兜底 | 10 s | App 自己的循环，间隔由内核给出 |

App 自己跑的时钟（嘉信轮询、报价盘口）用 `ms_live_stale_after_intervals` 取同一个倍数。护栏两道：内核测试遍历 `Feed::ALL` 与 `Renewal::OWN_CLOCKS`，Swift 测试用反射遍历整份快照，凡是 `…StaleAfterMs` 都必须是正数——新加的字段当天就被覆盖。

自检：`maystock-e2e account 40`（每 6 秒拿 REST 对一次同一标记价下的浮盈与权益，报告标记价年龄分布与各推送源的状态）。

### 1.1 交易所是注入进来的，不是写死的

Swift 那一侧还有一条边界：`ExchangeVenue`。它是交易 infra 的**端口**，
`StrategyRunner` 只认这个协议，全文没有出现过 OKX。

```
StrategyRunner ──▶ ExchangeVenue（协议）──▶ OKXVenue ──▶ OKXRESTClient（行情）
                                        │                 + KernelTradeClient（下单与交易读取，内核签名）
                                        │                 + TradeBridge（CLI：账单流水；OKX 文档解析器）
                                        └▶ 换任何交易所：新增一个同级 conformance
```

接协议时刻意做窄：只放交易循环真正需要的东西（行情、下单、订单状态、成交、仓位、
账户）。订单簿、费率档位这类各家差异极大的能力留在具体适配器上，新交易所不必去实现
一个永远不会被问到的接口。

唯一的可选能力是 `alternativeSeries`（资金费率、持仓量、多空比）——协议扩展给了
默认空实现。这不是静默降级：缺失的序列对齐成 NaN，而 NaN 在内核里一律是**未知**，
依赖未知的信号永不触发。**没有这些数据的交易所会拒绝交易，而不是盲目交易。**

换交易所要改的只有 `AppState.venue` 那一行。

## 2. 这次重构真正买到了什么

不是性能。是**消除了一个结构性风险**。

重构前：
- `BacktestEngine.desiredDirection` —— 回测的信号判定
- `StrategyRunner.decide` —— 实盘的信号判定

两个独立的 Swift 函数，靠一句注释「Mirrors BacktestEngine.desiredDirection」约束它们一致。
任何一边改动而另一边忘了改，结果就是**实盘交易的规则与你回测过的规则不同**，
而且不会有任何报错 —— 这是量化系统里最贵的一类 bug。

重构后：只有一个 `decide::desired_direction`，回测在第 i 根调用它，实盘在最新已确认 K 线上调用它。
**它们不可能不一致，因为只有一个。**

[KernelGoldenTests.swift](../Tests/MayStockKitTests/KernelGoldenTests.swift)
里的 `theLiveDecisionMatchesTheBacktestBarForBar` 把这条性质钉成了测试：
逐根前推调用实盘决策，必须复现向量化回测得到的同一串信号。

- **K 线走裸 `#[repr(C)]` 数组**：6000 根约 330 KB，每个 tick 序列化成 JSON 的开销比它喂的计算还大。
  `kernel/src/candle.rs` 里有一条单元测试断言 `size_of::<Candle>() == 56`，
  布局改了就编译期失败，而不是把价格当成时间戳解释。
- **配置与结果走 JSON**：它们小、形状会随功能变，手写一份 `BacktestResult` 的 C 结构体
  只会变成永久的布局 bug 来源。
- **编译后的策略是不透明句柄**：解析清单不免费，而实盘运行器每 20 秒就要用一次。
- **每个入口都包了 `catch_unwind`**：panic 跨 FFI 边界是未定义行为，
  而这个库被加载进持有交易所会话、并且会发单的进程里 —— 必须以错误字符串失败，不能以崩溃失败。
  这要求 release 用 `panic = "unwind"`：2026-09-25 之前是 `"abort"`，这道护栏编译出来什么都不做，
  任何 panic 都会直接带走整个 App。现在静态库里链接的是 `panic_unwind`（`ar t` 可查）。

## 4. 编译时就拒绝，而不是第一根 K 线上才炸

`CompiledStrategy::compile` 会拿 4 根假 K 线把每条表达式**真的跑一遍**。
这样未知函数、参数个数不对、周期非法都在导入时被拒绝。

刻意没有再写一张校验表：第二张表就是第二个需要与求值器保持同步的东西，
而它们不同步的那个场景，恰恰就是「策略导入时干干净净，然后在持仓状态下失败」。

## 3.1 `decide` 返回的是完整下单计划，不只是方向

```json
{ "target": -1, "targetExposure": -0.333, "targetBaseQuantity": -0.2051,
  "baseDelta": -0.0886, "shouldTrade": true, "haltDailyLoss": false,
  "reason": "敞口 -0.193 → -0.333" }
```

**仓位计算、再平衡阈值、日内亏损熔断三样都在内核里**，Swift 只负责把
`baseDelta` 发出去。运行器里不再出现任何 `sizing.mode` / `maxDailyLossPct` /
`rebalanceThreshold`。

之前这三样在 Swift 各有一份，而且**已经漂移了**：Swift 的 `riskPerTrade` 只认
百分比止损，遇到只声明 ATR 止损的清单会回退到满仓 —— 同一份清单，回测每笔冒
1% 风险，实盘押上全部预算。

`kernel/src/sizing.rs` 是这次抽出来的共用模块，回测的 `open_position` 和实盘的
`decide_live` 调的是同一个 `target_base` 与 `stop_distance`（定仓上限见 §3.23）。
[LiveSizingParityTests](../Tests/MayStockKitTests/KernelGoldenTests.swift)
把这条性质钉死：同一根 K 线、同样的资金，实盘计划开出的名义额必须等于回测开出的。

**保护性离场随单挂到交易所**：计划里的 `stopPrice` / `takeProfitPrice` 作为
`--slTriggerPx` / `--tpTriggerPx` 附在入场单上，由交易所 24 小时执行。
不用 20 秒轮询 —— 轮询会睡过止损存在的那根插针，应用关掉时更是完全不设防。
触发后按市价成交（`--slOrdPx -1`）：限价离场可能在它本要躲开的行情里一直挂着不成交。

**冷却与日内熔断也在内核**：`can_enter` 回测和实盘共用；熔断只锁当天，
UTC 日切换时由运行器清空 —— 回测正是这么做的，实盘若永久锁死，
回测收益里就含有实盘永远拿不到的次日交易。

一个刻意的设计：**取不到仓位大小时，`target` 仍然报出信号方向**，只是
`shouldTrade` 为 false。把它报成「空仓」会让调用方以为策略没有观点，
而事实是它有观点但执行不了 —— 状态栏要显示的正是后者。

**时间栅栏（`risk.maxHoldBars`）**：止损和止盈限制价格能走到哪里，却没有限制
仓位能躺多久。一笔论点已经不成立、但既没打到止损也没打到止盈的交易，会无限期
占着资金。这是 Triple Barrier 的第三条边，同样只有 `desired_direction` 一份实现。

它**压过包括反手在内的所有信号**：让反手绕过时间上限，等于在它最该生效的震荡行情
里让它形同虚设。到期就平，要不要再进场是下一根 K 线的新决定，照样受冷却约束。
编译期会拒绝 `maxHoldBars < minHoldBars` —— 那条仓位既不许平又必须平。

> 顺带修掉一个隐藏很久的 bug：`StrategyPositionState` 记录的开仓时刻从不清零，
> 于是「持仓多少根」算的是**策略有史以来第一笔成交**至今。`minHoldBars` 因此几乎
> 从不生效（无害），但时间栅栏会在开仓瞬间就把仓位平掉。现在它随平仓清空、
> 随反手重置。

## 3.2 交易所会做我们没让它做的事

内核算得再对，也架不住仓位在它背后被改掉。这几件事只可能在 Swift 侧处理，
但每一件处理错了都会让「内核以为的仓位」和「真实仓位」分叉。

**下单超时不是下单失败。** 请求可能已经到了交易所并成交。当成失败会把一笔真实
仓位留在台账之外、且策略已停无人看管。所以未确认的订单会被记下来，下一个 tick
开头先向交易所核实（早于任何新决策 —— 拿着账上没有的仓位去定仓会让错误复利）。
只有「交易所根本没这单」才允许重试；部分成交后被撤的仍算成交。

**交易所侧的平仓要补记。** 我们特意把止损附在入场单上让交易所 24 小时执行，
可它触发时成交带的是交易所自己的单号，不是我们的 `clOrdId` —— `ingestFills`
会跳过它，台账继续以为仓位还在。强平、ADL、手工平仓长得一模一样。
**幽灵仓位比不准的仓位更糟**：下一次定仓会按不存在的币去算，平仓会去卖不存在的东西。

对账规则，每条都是刻意的：

| 规则 | 为什么 |
|---|---|
| 只对永续 | 现货余额混着用户本来就有的币，差额不能证明任何事；永续是逐合约上报的，也正是会被强平的那个 |
| 查询失败绝不当成「已平仓」 | 否则每次网络抖动都会记一笔强平 |
| 要两次一致的读数 | 刚成交的单不会同时出现在成交和仓位两个接口上 |
| **只吸收减少方向** | 多出来的是别人的单（手工、别的机器人），并进来会让策略去平掉用户故意开的仓 |
| 优先领取交易所自己的成交记录 | 止损成交在止损价，不在一分钟后的标记价；真成交还带着真手续费 |
| 同一合约多策略时熔断，不按比例分摊 | 强平打的是净腿，拆不出是谁的钱亏了 —— 按比例分是编故事 |
| 补记后记入退出 bar | 被交易所平掉也是一次退出，冷却照样算，和回测一致 |

**移动止损：内核算价位，Swift 只负责搬。** OKX 自己有移动止损单
（`algo trail --callbackRatio`），逐笔跟，比我们紧。**没有用它**——它按每一笔成交跟，
回测按 K 线极值跟，把活交给一个行为不同的机制，等于跑的策略不是测过的那个策略。
内核每根 K 线报出 `trailingStopPrice`（**包括不交易的那些 bar**，因为价位会动而仓位不动），
Swift 用 `algo amend` 原地改价。用 amend 不用撤单重挂：撤掉的那一刻仓位是裸的，
而那正是快速行情吃掉你的窗口。两根 bar 之间交易所守的是上一档价位，所以仓位从不裸奔，
只是按它被测试过的节奏收紧。

止损的**地板**是开仓时那道固定止损，其 ATR 取的是**下单决策那根 bar**（成交前一根）——
和回测定仓用的是同一根。取当前 bar 会让地板随波动率漂移，而一道会随行情转平而放宽的止损
不叫止损。

**交易所拒绝附加止损时不放弃这笔交易。** OKX 会因为触发价离标记价太近或太远
而拒单。因为**保险**不被接受就放弃**信号**是错的取舍：改发裸单，然后由运行器在
tick 上盯这个价位，并明确告诉用户「App 关闭期间不受保护」。
前提是能区分「交易所明确拒绝」和「结果未知」——`TradeError.exchangeRejection`
只在响应里带着非零 OKX 错误码时才返回值；超时和 socket 错误一律算未知，走上面的核实流程。

## 3.3 回过头量一量：实盘到底跟上回测没有

回测说 +67%，实盘跑成 −3%，这件事越早变成一个屏幕上的数字越好。
`kernel/src/reconcile.rs` 回答两个问题，都从数据来，不从假设来。

**实测滑点。** 回测按 `slippageBps` 收费，那个数是人拍的。每一笔真实成交拿去和
**它落在的那根 bar 的 open** 比——正是回测建模的东西（bar *i* 收盘出信号，
bar *i+1* 开盘成交 + 滑点），所以算出来的数可以直接和清单里的假设比，而不只是「差不多」。

几个刻意的选择：取**中位数**而不是均值（一笔打在插针上的成交不该定下未来所有回测的成本），
但**同时报 P90**（只看中位数的成本模型，会在最需要的时候准备不足）；
**保留占了便宜的成交**（市价单偶尔有价格改善，扔掉它们会让估计系统性偏高）；
成交落在 K 线窗口之外就**不计数**，而不是拿旁边那根凑。样本少于 10 笔不给建议值——
拿三笔成交去改成本模型，只是把一个猜测换成一个更自信的猜测。

**净值对照。** 把回测净值按时间对齐到实盘净值上比。对齐是**阶梯式**的
（每个实盘采样点配最近一个不晚于它的回测点），不做插值——插值等于编造模拟从未报过的净值，
而两根 bar 之间恰恰是回测没有意见的地方。超出回测窗口的实盘采样点**直接丢弃**，
否则它们全会配到最后一个回测值、被当成回测走平，读起来就成了实盘跑赢。

报三个数，各答一个不同的问题：

| 指标 | 回答 |
|---|---|
| 收益差 | 差多少 |
| 跟踪误差 | 每一段的差异有多不稳定 |
| 形态相关性 | **是同一个策略成本更贵，还是压根在做另一件事** |

相关性在曲线不够波动时报 **null 而不是 0**——0 读起来是「不相关」，实际是「无定义」。
判据是相对下限而不是「方差 > 0」：一条按固定利率复利的曲线，收益方差是 1e-33 而不是 0，
除下去会得到一个完全由舍入误差构成、看起来却很自信的数。

这两件事本可以在 Swift 里做。放在内核，是因为它们是对市场数据的确定性计算，
**答案不该取决于是谁在问**。

这两条同时要求实盘净值必须是**按策略**的：账户净值把所有策略混在一起，
回答不了「这一个策略跟上它自己的测试没有」。于是 runner 每分钟给每个有配额的策略
单独采一个净值点（停掉的也采——停掉的策略仓位照样在动，曲线缺一段会把跨越缺口的收益算错）。

## 3.4 三道闸门：数据、订单、组合

调研顶尖量化框架后补的三层防护。共同点是：**它们保护的不是策略的判断，而是策略判断错时的后果**。

**行情质量（`kernel/src/quality.rs`）。** 回测拿到的是干净连续的数组，实盘拿到的是交易所
当时返回的东西——可能是一根陈旧的 bar、一个本该有 bar 的洞、或者同一根 bar 两次。
下游每个指标都会从中算出一个数，而那个数看起来和真的一模一样。
所以序列在信号之前先被检查，**数据不干净时拒绝决策**——注意是拒绝决策，不是给出空仓目标，
否则行情打个嗝就会把仓位平掉。

阈值都不是零：容忍 2% 以内的缺口（稀薄市场里交易所确实会偶尔丢 bar，为一个洞停一整天
是另一种失败），落后 2.5 根才算陈旧（bar 要等下一根开出来才确认，健康的行情源本来就落后
一整根）。回测传 `now_ms = None`：历史数据按定义就是陈旧的，这条性质在那里没有意义。

「缺口」和「落后」都按市场日历数（§3.20）：美股序列周五 15:30 到周一 09:30 之间没有 bar
不是洞，周六早上落后 18 根也不是断线。盘前盘后的 bar 不在日历网格上，只报 `offGrid` 计数，
不拒绝——那多半是行情源在给延长时段的数据，值得知道，不值得为它停机。

**下单前风控（`kernel/src/guard.rs`）。** 学 NautilusTrader 的 RiskEngine。定仓本来就有预算和
杠杆两道上限，所以正常情况下这里永远不触发——**这正是重点**。它拦的是不正常的情况：
止损距离算成了一个舍入误差、标记价读到一根坏 tick、清单被改成 `fixedQuote: 1000000`。
每一种都会产出一个定仓函数乐于返回的数字。

三条规则值得说明：**非有限的下单量在任何状态下都拦**（那不是一笔大单，那是算错了）；
**减仓永远不受尺寸上限约束**（拒绝平仓，正是保护性限额变成它本要防止的那个东西的方式）；
熔断跳进的是 `Reducing` 而不是 `Halted`——**停摆的引擎平不掉那个让它停摆的仓位**。

**组合级保护。** 学 Freqtrade 的 MaxDrawdown 与 StoplossGuard。
单策略日内熔断看不见四个策略各亏 4%，而那正是该收手的一天。连续止损保护则是因为：
策略可能完全按设计工作、每一次止损都触发得对，账户就这么一次一次正确的止损里流干。

## 3.5 这个回测结果里有多少是「看得多」

`kernel/src/overfit.rs`。搜一千组参数，最好的那组夏普一定好看，无论其中有没有一组真有边际。

- **Deflated Sharpe**：观察到的夏普在「无技能」原假设下有多大可能，同时修正试了多少次
  和收益分布的偏度峰度。偏度峰度不是装饰：夏普估计量自身的标准误就取决于它们，
  而**小步稳赚、偶尔巨亏**恰好是朴素优化器最容易走进去的形状。
- **PBO（CSCV）**：把序列切成连续块（不打乱——打乱会破坏交易策略收益的自相关性），
  穷举所有对半切分，看样本内冠军在样本外落到中位数以下的比例。
  它验的是**选择过程本身**，所以能抓到「每个单独回测都没问题、但这次搜索换一段数据
  就会选出另一个冠军」。

两个都要，因为它们答的不是同一个问题：DSR 可能放行一个边际真实但微弱的策略；
PBO 能抓到搜索本身是坏的，哪怕每个回测单看都体面。

两处刻意的处理：并列名次取**中位排名**（把并列判成赢，等于说冠军赢过了它其实只是打平的对手，
而近乎相同的候选正是过拟合搜索的产物）；相关性/显著性在曲线不波动时报 **null 而不是 0**。

还有一条值得记下来，免得以后有人来「修」：标准误是**双向**加宽区间的。
观察到的夏普已经低于门槛时，估计越不可靠，我们对「它低于门槛」这件事也越不确定，
概率是往 0.5 走而不是往 0 走。这不是 bug，测试里专门钉了一条。

`Statistics.expectedMaxSharpeUnderNull` 的 Swift 实现已删除，优化器改调内核。

## 3.6 参数寻优：整轮在内核里跑完

原来每个网格点都要：Swift 重新编码清单 → `ms_strategy_compile` **重新解析每一条表达式** →
跑回测 → 把六千个净值点和全部成交序列化成 JSON → Swift 解析回来 → **只读六个数**。
五千次，串行，单核。

三个观察让它塌缩掉：

1. **参数值不改变解析后的表达式。** AST 只取决于源文本，网格点之间只有 `params` 不同。
   所以一个候选是「克隆编译好的策略 + 换一张 map」，不需要词法、语法、校验。
2. **寻优只需要 metrics。** 曲线和成交列表正是让结果序列化变贵的东西，而寻优两个都不看。
3. **网格点彼此独立。** 除了只读的 K 线，没有共享状态。

剩下的就是一个对克隆结构体的并行循环，和最后一份很小的 JSON。

实测（1000 组参数 × 6000 根 K 线，M 系列）：

| 路径 | 每候选耗时 |
|---|---|
| 旧：重新解析 + 全量结果 JSON | 0.400 ms |
| 新：单线程 | 0.148 ms |
| 新：自动线程数 | **0.042 ms** |

**9.5×**，而且这还没算旧路径在 Swift 侧额外付的 JSON 编解码。

两处刻意的设计：结果**按网格顺序回填**（用一个 slot 数组而不是追加），
因为**输出取决于线程调度的回测不可复现，而不可复现的回测不算证据**；
交叉验证的收益序列走**第二遍重跑**而不是第一遍全存 —— 重跑二十几次回测，
比在内存里攥着五千条净值曲线便宜得多（6000 点 × 5000 组 = 四分之一 GB 的 f64，
存下来只为了扔掉）。

`with_params` 会**按清单声明的 min/max 夹取**：调用方不能靠传一个范围外的数
来扩大参数的定义域。求值不了的网格点（周期为 0、NaN）被跳过并**计数上报** ——
跳掉了大半个网格的搜索什么也没找到，无论冠军长什么样。

## 3.7 回测的完整性

- **回测报告现在说明它跑在什么样的数据上。** 跨越缺口的 60 根回看窗口，覆盖的市场时间
  多于 60 根。实盘会直接拒绝这样的序列；回测无法事后拒绝，所以它如实报告。
- **回测应用与实盘同一套下单前限额。** 只有定仓 bug 才会触到它们，而这正是 bug 该浮现的地方：
  一份悄悄模拟了实盘会拒绝的订单的回测，是不能拿去交易的回测。
  **但交易状态机不套用** —— 组合回撤刹车是实盘风控，不是策略的规则，
  把它折进模拟等于测了另一个策略。

## 3.8 一个咬了我两次的坑，已变成一条测试

SwiftPM 跑不了 cargo，所以 `Scripts/build-kernel.sh` 负责暂存静态库，
`swift build` 链接暂存的那一份。改完 Rust 直接 `swift test`，**测的是上一版内核** ——
而且是无声的：Rust 里新加的字段在 Swift 侧解码成 nil，症状看起来像逻辑 bug。

现在有一条测试比较暂存库和最新 `.rs` 的修改时间，失败时直接说「先跑 build-kernel.sh」。
一条会说话的失败，比构建脚本里的一句注释值钱。

## 3.9 Walk-forward 的 purge 与 embargo

样本外那一段必须自带预热，指标才能像实盘一样起步 —— 这意味着**分割点之前那些 bar
喂养了测试期的第一批信号**。用同一批 bar 去拟合参数，就是教科书上的泄漏：
训练集里含有测试集依赖的观测。

所以拟合窗口在它们之前 `warmup` 根就停下（**purge**），再往前留 `embargo` 根
（默认每折 1%，López de Prado 的做法）。purge 只删掉测试**机械上**需要的东西，
而价格是序列相关的，边界两侧描述的几乎是同一个市场状态 ——
一直拟合到边缘，就是拟合到测试集本身。

协议参数**写进报告**而不是靠默契：折数、样本内占比、purge 根数、embargo 根数。
一份没写下这些的 walk-forward 没法和另一份比较，而它们的差别，
正是「真正的样本外测试」和「延迟了一点的样本内测试」之间的差别。

## 3.10 有效独立注数：两个 0.95 相关的策略是一注加倍

给每个策略单独配资，不等于在策略之间做了分散。BTC 和 ETH 上的两个趋势跟踪，
在崩盘时会一起走 —— 而那正是分散本该起作用的时刻。于是这个组合是**一个双倍大小的仓位**，
而任何单策略回测都看不出这一点。

`reconcile::diversification` 算全部两两相关性和**有效独立注数** `N² / ΣΣ ρᵢⱼ`：
N 个完全相同的策略，这个数是 1。

一处刻意的处理：**只要有一对相关性无法定义，整个有效注数就报 null**。
把未定义当成 0 相关，等于把一条走平的策略算成免费的分散来源。

## 3.11 换个成交顺序会怎样

回测报出一个最大回撤。那个数字是**分布里的一次抽样** —— 同样这些交易换个顺序，
最难受的那一段就不一样，而它们碰巧到来的顺序，对它们下次到来的顺序没有任何信息量。

后果很直接：观察到 31%、重采样 95% 分位 44%，那么定仓和组合熔断该按 **44%** 建。
回测报出的那个是这个策略能对账户做的事情里**乐观的那一尾**。

`kernel/src/resample.rs` 提供两种方法，因为它们回答不同的问题：

- **shuffle** 保留每一笔交易只改顺序 —— 问「回撤里有多少是顺序造成的」。
  每笔只出现一次，所以复利可交换，**终点不会动，动的只有路径**。
- **block bootstrap** 有放回地抽连续片段 —— 同样的问题，但保留聚簇。
  连亏不是独立抽样，把它们打散的方法会**低估它本要度量的那条尾巴**。

块长是**建模选择而不是自由参数**：在一段五赢五输交替的数据上，块长 10 无论从哪切
都恰好含五赢五输，尾巴被抹平；块长 5 才能把连亏叠起来。这条专门写了一个测试记着。

随机数用固定种子的 LCG，不是系统随机源：**每次算出来都不一样的风险数字没法被质疑，
而没法被质疑的数字不能被信任**。取模用拒绝采样而不是直接 `%` —— 偏差很小，但省掉它是免费的。

爆仓的序列在 0 停住，不继续复利成负权益 —— 那会模拟一笔交易所早就强平掉的负债。

> 这一条本身就抓到过一个 bug。第一版接线把 `returnPct` 当成小数喂进去，
> 于是一笔 −20% 的交易变成 `1 + (−20)`，报出「回撤 100%」。
> 数字荒谬到一眼就能看出来 —— 而根因是内核那条注释写着「as a fraction」，
> 值却乘了 100。注释已改，Swift 侧也加了 `returnFraction` 让单位不再靠记忆。

## 3.12 高周期过滤器与对齐

`AlternativeSeriesSpec.bar` 现在可以粗于策略自身的周期 —— 小时级策略上挂一个日线趋势闸门。
这需要先修对齐规则。

K 线的时间戳是**开盘时间**。原来的对齐只比较开盘时间，同周期下恰好是对的
（决策发生在 bar 收盘，那一根的收盘价此刻已知），但一旦允许粗周期，
它会把一根还有 23 小时才收的日线的**收盘价**交给凌晨一点的小时 bar —— 23 小时的未来函数，
正是高周期文献里叫 repainting 的那个失败。

现在的规则是「到本 bar 收盘时它自己是否已经确定」，而两类数据在边界上**真的不同**：

| 类型 | 规则 | 为什么 |
|---|---|---|
| 按 bar 度量（另一标的的收盘） | `obs.ts + obs周期 <= 本bar收盘` | bar *i* 自己的收盘价在 bar *i* 收盘时可用，这是执行模型本身 |
| 时点发布（资金费结算） | `obs.ts < 本bar收盘`（严格） | 落在决策同一刻的数据，假设你已经握有它是乐观读法，而乐观读法正是让回测撒谎的东西 |

`candleSeconds` **没有默认值**：答案取决于它，一个没想清楚自己何时决策的调用方
不该靠碰巧拿到正确的对齐。

顺带修正了一条更早的测试所编码的规则：它断言「发布于 bar 开盘之后的值就是未来函数」。
保证的是**决策时刻**，而决策在 bar 的收盘。发布在 bar *i* 之内的数据，
bar *i* 的信号确实握有它，拒绝它等于模拟一个实盘并不存在的滞后。
真正不能碰的是发布于该收盘**之后**的数据 —— 现在测的是这一条。

## 3.13 连续敞口引擎缺的两道闸

回测两条引擎：二值（进出场）和连续（按比例持仓）。风控条款一直只加在二值那条上，
而**线上两个 volscaled 策略正是连续型**。

**日内熔断。** `decide_live` 在分支到敞口之前就检查 `maxDailyLossPct`，
所以**实盘对连续策略是执行熔断的**；`continuous.rs` 完全没有这段。
一份继续交易的模拟，会把运行器本该坐视不动的那些天的收益也算进去。
熔断只锁当天，UTC 日切清除 —— 否则回测会拒绝运行器明天照常会做的交易。

**强平。** `liquidations: 0` 是写死的。一个 5 倍杠杆的连续仓位，
可以在模拟里一路扛过 40% 的下跌到回测结束 —— 交易所绝不会允许。
连续仓位每次再平衡都在变大小，所以强平价按**当前持仓**重算，而不是在开仓时定死。
强平价的算法抽成 `liquidation_buffer`，两条引擎共用一份定义。

## 3.14 心跳：进程活着，但循环停了

`tickStallTimeout` 只能救活卡住的**单次** tick。整个 loop 死掉、app 被杀、
笔记本睡过去之后，没有任何信号 —— 什么都不报错，面板继续显示它最后拿到的数字，
账户只是不再有人管。这正是运维文献里 dead man's switch 要解决的那类失败：
**「进程还在，但它已经不做那件事了」**。

所以引擎主动说「我还在干活」，而**这个信号的缺席**才是警报。落盘而不只是留在内存里，
因为要回答的问题是「我没看着的时候它在跑吗」，而内存里的值在重启之后回答不了。
写入有节流（30 秒），tick 频率远高于这件事需要的分辨率，而每次写都是交易循环里的磁盘 I/O。

心跳告警**盖过**组合保护的横幅：暂停是一个决定，而循环死了是一个没人管的仓位。

## 3.15 心跳报的第一个真警报：子进程把 tick 永久挂住

心跳上线后报出的第一件事不是误报，是真的：**交易循环 143 分钟没有完成一次轮询**。
根因在 `TradeBridge` 的子进程看门狗里，一行看上去无害的提前返回：

```swift
DispatchQueue.global().asyncAfter(deadline: .now() + timeout) {
    guard process.isRunning else { return }   // ← 没有 resume continuation
    ...
}
```

`okx` CLI 是个 node 程序，它会**留下一个继承了 stdout 的后台子进程**（版本检查之类）。
于是父进程立刻退出，管道却还开着：`readDataToEndOfFile` 永远读不到 EOF，
15 秒后看门狗醒来一看 `isRunning == false`，认定「没有要杀的东西」就直接返回了 ——
**continuation 再也没有人 resume**。调用方就此永久挂起。

在交易循环里，这意味着 tick 再也没有回来。没有报错、没有退出，面板照旧显示它最后
拿到的数字，只是仓位从此无人管理。这就是 3.14 那个死人开关存在的全部理由，
而它确实抓住了。

两条修法，都收拢进 `Subprocess`（`okx` 桥和外部脚本引擎此前各写了一份，
**同一个 bug 也各写了一份**）：

- **超时无条件 resume**。还活着的孩子照杀，已经走掉的照报。进程死没死，
  跟「调用方该不该被唤醒」本来就是两件事。
- **改用 readability handler 排空管道，不再阻塞读**。原来每个调用要占住两个线程等
  EOF；一个反复卡住的 CLI 会把全局队列的线程池耗光，而看门狗自己就排在那个池子上 ——
  修好第一条也会被第二条重新拖死。

还有一条结构性的：**循环不再 `await` 单次 tick**。

```swift
runner.beginTick()          // 发射不管落地
try? await Task.sleep(...)  // 循环自己掐表
```

原来 `await runner.tick()` 让整个引擎的存活挂在每一次 tick 都必须返回上，
这个假设一旦破掉就是永久性的。现在超过 `tickStallTimeout` 的 tick 会被
**取消并替换**：取消而不是遗忘，因为它万一真的返回了，握着的是几分钟前的价格、
仓位和 K 线 —— `submit` 与逐策略循环都会在下单前先看一眼 `Task.isCancelled`。
被放弃的 tick 也**不上报心跳**：拿一次没干活的轮询去报平安，正好盖住这套机制要抓的东西。

## 3.16 覆盖率量的是密度，不是两端距离

3.15 那次停摆还留了后半截没补。`EquityChange` 的文档说它「明确交代这个窗口里有多少
是真实采样撑起来的」，但 `coveredSeconds` 实际算的是：

```swift
coveredSeconds: endTs.timeIntervalSince(start.ts)   // ← 两端距离
```

**首尾横跨一天的曲线就是横跨一天，中间缺多少都一样。** 于是那天引擎死了 72%，
面板照样认为 1d 窗口 100% 覆盖，`isComplete` 为真，一个自信的收益率就这么打了出来 ——
它是拿一天里零散的三个半小时算出来的。

现在按**采样密度**算：逐对累加 `min(间隔, 容忍度)`，超出容忍度的部分是窟窿，不计入。
容忍度刻意取 300 秒，和心跳判定「引擎没在跑」用的是同一个数 —— 横幅和覆盖率
不该对「这段时间算不算被观测过」有两种说法。超过 `fineHorizon` 的部分曲线本来就被
抽稀到 `coarseInterval`，那一段用 `coarseInterval * 2`，否则会把我们自己的压缩报成停摆。

`spannedSeconds` 单独留着，因为两者要分开回答两个问题，而 UI 需要这个差别：

| | 含义 | 面板 |
|---|---|---|
| 跨度不足 | app 刚装上，还没记那么久 | 灰色「记录 20 分钟」 |
| 跨满但有洞（`hasGaps`） | 引擎当时没在跑 | **红色「缺 6 小时」** |

拿真实数据回测这条改动，当天曲线的 1h 窗口从「100% 覆盖、照常出数」变成
「44.8% 覆盖、缺 0.6 小时」。抖动不算窟窿：实际采样是 60–120 秒一个点，
遇上慢的 CLI 调用还会更长，容忍度按 300 秒给，不会每小时喊一次狼来了。

## 3.17 收益率窗口：一个滚动，两个日历

三个窗口原本都是滚动的，于是「7d」在装上第二天必然是空的 —— 它得等够七天。
但交易员早上问的从来不是「过去 24 小时」，而是**「今天赚了多少」**，而这两个是不同的问题。

改成一个滚动、两个日历，全部按**新加坡时间**（这本账簿结算所在的时区）：

| 窗口 | 起点 |
|---|---|
| `1h` | 滚动，最近一小时 —— 会在你眼皮底下动的那个 |
| `今日` | 当天 00:00（SGT） |
| `本周` | 本周一 00:00（SGT，`firstWeekday = 2`） |

日历窗口的好处不只是语义对：**它开机一秒就能算**。00:00 是一个真实时刻，
只要曲线里有一个不晚于它的采样，「今日」就是精确值 —— 而滚动窗口那时还在等着填满。
曲线本来就落盘，所以重启不影响：参考点是磁盘里那个跨过午夜的采样，不是文件的第一行。

**数字永远显示。** 之前覆盖率不足就打一个横杠，对日历窗口是错的交易：
横杠什么也没告诉读者，而「+0.4%，自 10:23 起」既给了数又给了限定。所以警示不再**替换**
数字，而是跟着它走 —— `*` 表示曲线起点晚于锚点（app 还年轻），`!` 表示锚点够得着
但中间有洞（引擎当时没在跑，见 3.16），两者都在 tooltip 里说清楚。

`isAnchored`（参考采样 ≤ 锚点）和 `coverage`（密度）是两个独立的问题，
UI 需要这个区别：一个是「我们还没记那么久」，另一个是「那段时间没人在跑」。

## 3.18 菜单栏空转烧掉五分之一个核

macOS 两次把 app 标记为持续高 CPU。实测空闲稳态 **20.5% 单核**，只挂了两个监控项。

`StatusItemController.render()` 每次都会：把 60 分钟窗口切出来（fine 层 1 秒 1 点，
即 **3600 个点**）、`map` 出价格数组、`downsample` 到 60 个、再光栅化一张 NSImage。
而渲染节流是 100ms —— 也就是 10Hz × 2 项。

但 `SparklineBuffer` 的 `fineInterval` 是 1 秒：**它每秒最多接受一个采样**。
所以 10Hz 里有九次画的是完全相同的数据。按「最新采样的时间戳 + 窗口分钟数」缓存图片，
只有序列真的往前走了才重画：**20.5% → 5.9%**。

价格文字仍然按原节流走 —— 那部分是纯字符串，便宜，而且是用户真正在看的东西。

## 3.19 期权：一个新的品种家族，而不是一堆特判

`InstrumentType` 现在有三个成员：`Spot`、`Swap`、`Option`。加第三个成员时把
原来散落在十几处的 `== .swap` 全部收成**声明**——每个家族自己回答
「交易所按合约还是按余额报仓位」（`isDerivative`）、「走哪个 CLI 模块」
（`cliModule`）、「下单要不要带腿」（`usesPositionSide`）、「结不结资金费」
（`settlesFunding`）——运行器只问这些属性，不再问品种名。对账、成交摄取、
敞口统计因此对期权自动生效，而不是各写一遍。

**信号读标的，仓位是合约。** `market.instId` 是信号所读的 K 线（`BTC-USDT`），
`options` 块决定合约怎么挑。做多买看涨、做空买看跌，**只买不卖**：
卖出期权的亏损无上限、靠交易所保证金约束，两样都没建模，所以不许写。
内核的决策接口多了一个 `optionPlan`：`open`/`close`/`flip`，带权利金预算
（`equityPct` 和 `riskPerTrade` 在这里是一个意思——权利金就是全部风险）、
最短到期天数、行权价偏移和权利金止损止盈百分比。张数取决于交易所此刻的卖一，
所以由运行器拿着限价问内核（`ms_option_purchase`），内核按回测买入的同一个规则
（`options::affordable_purchase`，权利金加手续费不超过预算，§3.23）给出张数。

**挑合约的规则只有一份**（`options::select_contract`）：最近一个到期 ≥ N 天的合约，
在它上面取离目标行权价最近的一档，平手时取更贴近现价的。实盘把交易所期权链
喂给它（`ms_option_select`），回测把模型生成的链喂给它。两边不会挑出不同的东西，
因为挑的是同一个函数。

**回测是模型定价。** OKX 不保留已到期合约的行情，所以 `backtest/options.rs`
用 Black–Scholes（r = 0）按标的收盘价与「实现波动 × `impliedVolMultiplier`」
定价：入场按下根开盘定价并加滑点；止损止盈按权利金、在**收盘**判定（模型没有
盘中路径，这比交易所在权利金 tick 上触发晚一根）；含到期时刻的那根**开盘**
按内在价值结算、不收费；手续费按 OKX 规则——名义额 × 费率、封顶权利金的
12.5%，两半都要：没有封顶，深度价外的便宜合约会比它本身还贵；没有名义额基准，
深度价内的贵合约会显得几乎免费。没有强平也没有资金费——多头期权亏不过权利金，
也不付 carry；`funding_unmodelled` 因此是 false，不是「没建模」。
报告和工作台都标注「模型价」，它能诚实回答的只有「方向信号赚不赚得回权利金」。

**实盘用真实盘口。** 运行器读链、读买一/卖一/标记价/指数价，
把预算按 `卖一 × 指数 × 每张标的量` 换成整张，IOC 限价（卖一上浮 2%）成交；
平仓是 reduceOnly 的 IOC 卖单。没有卖盘、或卖一高出标记价 25%（空盘口的占位挂单，
模拟盘上真见过 3000 BTC 的卖一），不开仓并说明。止损止盈按权利金标记价在 tick 上
本地执行。到期后交易所把仓位结算掉，对账把它当作一次外部减仓补记，注记写「到期结算」。

**账本换算在成交那一刻做一次。** OKX 期权以结算币（BTC）按每单位标的报价，
手续费也是 BTC；账本记计价币，所以成交按交易所盖在成交上的指数价
（`fillIdxPx` / `fillPxUsd`）换算，没有就用本轮读到的指数价；两者都没有就不入账、
留到下轮，绝不猜一个数。`contractSize` 对期权是 `ctVal × ctMult`——
BTC 期权的 0.01 写在 `ctMult` 里而不是 `ctVal`，只读 `ctVal` 会把每张合约当成 1 BTC，
下单量放大一百倍。这条现在是 `InstrumentMeta.contractValue(ctVal:ctMult:)` 一个函数，
永续走的也是它。

**仓位方向和观点方向分开。** 账本里买入看跌是「多头合约」，对内核却是「看空观点」；
`StrategyPositionState.signalDirection` / `kernelHeldBase` 负责翻译，
运行器把它们而不是 `direction` / `baseQuantity` 交给内核。
一个策略一次只持一个合约：空仓时账本可以换到新合约（换月），持仓时收到别的合约的
成交则先不入账、写日志、下轮重试——两个合约的均价算术没法揉在一个仓位里。

## 3.20 去「7×24」化：日历、费用组件、品种政策

接美股之前，内核有三处把「加密货币交易所」当成了「市场」本身：一年 365 天连续交易、
手续费是双边按名义额收的百分比、做空与杠杆是永续合约的专属。三处各自散在
`metrics.rs`、`decide.rs`、`ffi.rs`、`quality.rs` 和 Swift 的 `BacktestReport` 里，
每处都对，加起来就是一个只认识 OKX 的内核。

**市场日历（`kernel/src/calendar.rs`）。** `MarketCalendar { Continuous, UsEquities }`，
由清单的 `market.venue` 决定。它是唯一一份「bar ↔ 时间」的换算：一年多少根
（连续市场 365.25 天；美股 252 个交易日，日内按每日交易时段向上取整的 bar 数）、
一根什么时候收（15:30 那根一小时 bar 16:00 就收）、两个时刻之间该有几根开盘
（持仓多少根、冷却过了几根）、一个时刻属于哪个交易日（日内亏损闸复位的边界，
美股按纽约本地日期，跨 UTC 午夜的一个交易时段仍是同一天）。纽交所的节假日规则、
提前收盘、临时休市、夏令时都在这里，靠 `chrono-tz` 的 `America/New_York`。
连续市场的网格锚点由交易所定（OKX 日线锚在 UTC+8，不在纪元），所以「两个时刻之间几根」
从调用方给的那根 bar 往回数，而不是除以间隔取整——10:05 进场、15:00 那根判断，
是五根不是 4.9 取整的四根。这条以前在 Swift 里修过一次，现在只在内核里有一份。

**费用组件（`kernel/src/fees.rs`）。** 手续费从一个 bps 数变成 `FeeComponent` 列表：
按名义额（bps）、按数量（每股）、按单（每笔），各自分买 / 卖 / 双边，可带单笔上下限。
嘉信美股买入零佣金、卖出收 SEC §31（按成交额）与 FINRA TAF（按股数、封顶），
用百分比根本写不出来。清单的 `costs.feeBps` 仍可写，是「双边名义额比例」的简写，
和 `costs.fees` 二选一。品种没有默认成本（美股佣金是券商的选择、监管费年年改）时，
内核不会当成零，`BacktestConfig` 必须给，Swift 侧从 `FeeSchedules` 按 venue 解析。
期权走同一套：`options::option_fee` 先把组件按标的名义额算一遍，再按 `feeCapPctOfPremium`
封顶，所以「只在卖出时收」这类组件对期权同样成立。

**品种政策（`kernel/src/strategy.rs` 的 `InstrumentPolicy`）。** 能否做空、杠杆上限、
是否按张计价、保证金制度（永续逐仓 / 美股 Reg T）、默认维持保证金率、默认费用，
全部只在内核里声明一次，`ms_instrument_policy` 吐 JSON 给 Swift。
`InstrumentType` 多了 `STOCK`：可做空（保证金账户）、杠杆 ≤ 2、按股计价；§3.19 的
`OPTION` 也在同一张表里（可做空即买看跌、不许加杠杆、按张计价、无保证金制度）。
强平缓冲按制度算：逐仓是 `(1 − 维持率) / 杠杆`，Reg T 是 `1 − (1 − 1/杠杆) / (1 − 维持率)`。

**金标没有变。** 指纹（交易数 / 终值 / 收益率 / 回撤 / 胜率 / 手续费）不含年化数字，
而 OKX 策略的费用与日历行为逐 bit 未动，所以 `KernelGoldenTests` 不需重算——
这本身是一条验证：通用化没有在原有路径上改变任何一笔成交。

## 3.21 回测的每一笔平仓都是一次成交（2026-10-09）

**账本恒等式。** `最终权益 = 初始资金 + Σ 每笔净盈亏`，每笔 `净 = 毛 − 手续费 − 资金费`，
净值曲线的终点就是最终权益。测试（`every_engine_books_exactly_what_it_pays`）遍历仓库
`Strategies/` 里的全部清单——不管它路由到哪条引擎——再加上专门走到强平、反手、减仓、
正负资金费的场景。

它在旧代码上立刻抓到一个真 bug：连续引擎的资金费只写进成交记录，从没从权益里扣。
持仓时净值减掉了它，平仓时累计清零、权益又跳回去。仓库自带的 `btc-tsmom-short.json`
在合成数据上最终权益比账本多 1.96。现在每次减仓按平掉的比例真正扣，收尾平仓也扣。
一张单同时平掉一边、开出另一边时，手续费按两部分的数量拆开，平掉的那笔不再替新仓付开仓费。

**成交只有两种构造（`ExitFill`）。**

- 市价平仓——信号、日内熔断、收尾、止损、止盈、移动止损——一律加滑点、按费率表收费。
  止损止盈实盘是条件市价单（`trade::wire` 下单价 −1）；回测原来按裸价位成交，
  是唯一不付滑点的平仓，恰好美化了对成本最敏感的紧止损策略。
- 逐仓强平按破产价结算（`liquidation_fill`）：这笔仓位的保证金正好亏光，资金费和一笔
  正常平仓手续费都在其中，跳空再远也不多亏（May 10-09 定）。依据是 OKX 自己的平仓历史：
  一笔逐仓 5 倍 BTC 空单被强平，价格盈亏 −614.60、资金费 +14.12、平仓手续费 1.81，
  平仓这一下正好 −602.29，等于保证金 0.0324 × 92 945.9 / 5；连开仓费是 −603.79。
  旧规则按触发价成交再另收手续费，20 倍以上会亏得比保证金还多——交易所收不到那么多。
  强平触发价（`liquidation_buffer`）只决定什么时候，这里决定亏多少。
- Reg T 没有这条底：券商按市价卖，跳空穿过的部分照亏，加滑点。

**止损止盈的先后。** 原来是「这根 K 线碰到的线里取最差价」，现在是能确定的用确定的：

| 情形 | 判定 |
|---|---|
| 开盘就越过某条线 | 按开盘价成交——跳空越过止盈就是止盈，之后同根再跌到止损也不改 |
| 开盘越过强平线 | 判强平，即使止损更近：风控引擎按标记价立刻接管，止损的市价单来不及 |
| 同一侧两条线都在盘中碰到 | 先碰到的先成交：多头止损在强平线之上，先止损，强平被它挡住了 |
| 止损与止盈同根都碰到 | 盘中先后不可知，按止损（最坏假设） |

**反手不受冷却期限制，回测与实盘一致。** 实盘只在空仓入场时查冷却（`decide::decide_live`）；
二值和期权回测却拿反手前一次平仓来算反手开仓腿的冷却，于是冷却窗口里的连环反手只平不开——
一个运行器根本不会跑的策略。现在反手的开仓腿不受冷却，平掉的那笔记为新的离场原因「反手」
（`ExitReason::Reversal`），连续引擎一张单翻转时同样记反手，日内熔断的平仓记「日内熔断」而不是「信号」。
Swift 只留一个 `TradeExitReason`，直接从内核结果解码；原来两个重复枚举之间的转换会把不认识的原因
悄悄当成「信号平仓」。测试拿它和内核的 `ms_exit_reasons` 比，不再手抄一遍清单。

**守卫只量一张单新增的敞口。** 补反手测试时发现：`guard::check_order` 把反手整单——平掉的
加上开出的，满仓时是仓位的两倍——当成开仓去量。本分支早先把失控上限改成「定仓所能达到名义的
1.5 倍」之后，满仓反手在任何杠杆下都是 2 倍、必然被拒，连平仓也一起不发，仓位留在信号已经反过来
的那一侧；在 main 上（旧的统一 1 000% 上限）是 5 倍以上被拒。注释本来就写着「开仓那一半要像任何
入场一样审」，代码量的却是整单。现在限额只量新增的部分（`guard::opening_base`）；反手整单被拒时
——组合进入「仅允许减仓」，或者新仓超过单笔上限——退回为单独平仓（`guard::admit`），
实盘决策和连续回测发的是同一张单。只有「暂停」才什么都不发。

**金标。** `stopsAndTargets`、`atrRiskSizing` 因止损付滑点而变。另外查出 `trailingStop`
77 笔全是信号离场、`shortsAndLeverage` 一次止损都没触发——名字叫什么，恰恰没测什么。
每个金标现在声明自己必须走到的离场原因（`exercises`），走不到就失败；这两个夹具收紧到
1.5% 让机制真正触发，重新冻结。`MAYSTOCK_PRINT_GOLDENS=1 ./Scripts/make.sh test --filter
KernelGoldenTests` 会连离场原因分布一起打印，数字为什么动一眼可见。

## 3.22 分钟级回测：一次 20 万根，每个窗口 O(n)（2026-10-09）

May 定了支持 1m 研究、App 的全样本放开到交易所全部历史。这带出三条规则，各写一处：

- **一次最多多少根 K 线**：内核 `expr::MAX_BARS = 200_000`（约 139 天的 1m，永续上线以来的
  全部 1H），经 `ms_max_bars` 给 App 和实验台用，Swift 不再有自己的数。
- **单个窗口最长多少**：`MAX_PERIOD = MAX_BARS`，一次装不下的窗口没有意义。旧的一对数字
  （单窗口 5 000、一次 12 000）接受了 `ema(close, 5000)`，而它的预热是 15 000 根，永远开不了仓。
- **预热装不下就拒绝**：嵌套的 EMA 会叠加，单窗口上限挡不住，所以编译时检查整份清单的预热
  （`CompiledStrategy::warmup_for`，`compile` 与 `with_params` 原来各有一份，现在一份），
  装不进一次回测就拒绝——它既不能回测也不能实盘决策。

**每个滚动窗口都是 O(n)。** `highest`/`lowest` 用单调队列；`wma` 滑动普通和与加权和；
`stdev` 和波动率目标用的已实现波动率滑动「锚定矩」（`series::WindowMoments`）。
20 万根、窗口 10 080 实测：`highest` 5.9 s → 1.7 ms，`wma` 1.2 s → 0.4 ms，`stdev` 0.97 s → 1.5 ms。
优化器的每个网格点都要算一遍，原来的嵌套循环会让 1m 寻优不可用。

滑动方差有一个坑，实测踩到过：方差是两个大数之差，窗口里的噪声滑出去、一段平盘滑进来时，
差值只剩舍入误差——两根窗口的平盘读出 2.4e-7，真值是 0。所以 `WindowMoments` 把和保持在
窗口均值附近的锚点上，每滑过一个窗口长度就精确重算一次（锚点一起重置），方差相对于平方和
塌缩到 1e-6 以下时也立刻重算。旧的嵌套循环留在 `#[cfg(test)]` 里当参照，测试在 NaN 段、
平盘、BTC 量级的价格上逐根比对到 1e-9。

**下载**：全样本是几百到上千页。App 的每次 OKX 公共读取都按接口共用一个进程级的配速表（`OKXPublicPacer`，
candles 40、history-candles 20、资金费 10 次/2 秒，各留一点余量），因限频、服务端繁忙、断连或超时失败时
退避重试（0.5/1/2/4/8 秒，每次记日志）——读取不改变任何东西，内核的签名读取也是这条规则；
原来只有分页下载重试，一次冷连接超时就让单次报价失败（`maystock-e2e doctor` 四次里实测一次）；同一批回测在同一标的上共用一次下载（`BacktestHistoryMemo`，
只在内存、十分钟，运行器永远不读它）；实验台把单次回测拉到的数据整包交给分窗口报告，不再下第二遍。
OKX 只提供约三个月的资金费，永续全样本回测在此之前不计资金费——报告按第一根可交易 K 线
算出缺了多少天、占多少比例，写进覆盖说明。

## 3.23 开仓占用：保证金加开仓费不超过资金（2026-10-09）

**规则只有一条，写在 `sizing::Footing`。** 一张单开仓时，资金同时付出两样：交易所冻结的
保证金，和这笔成交的手续费。原来定仓只让保证金装进资金——`equityPct: 100` 把全部资金变成
保证金，手续费另付——于是：

- 回测里逐仓强平正好亏掉保证金（§3.21 `liquidation_fill`），满仓 10 倍、5 bps、一根暴跌后
  期末权益 −50.00，正好是负的开仓费，任何账户都到不了；
- 实盘交易所直接拒单（下面的实测）。

现在定仓的上限是「订单之后这笔仓位的保证金 + 这张单的手续费 ≤ 资金」。单一费率下就是
`名义 ≤ 资金 / (1/杠杆 + 费率)`；费率组件带下限、封顶或按单收费时这条线会弯，
`sizing::largest_within` 沿区间插值、隔一步二分地求解，返回的永远是算过、装得下的那一端。
它只限制一张单**新增**的部分：平仓、减仓、保持不动从不被削（与 `guard::check_order` 同一条线）；
反手的新方向在平仓手续费付掉之后定仓。所有定仓都经过它：二元回测的 `open_position`、
连续回测（决策和成交两处）、期权回测、`decide_live` 的二元与连续两支，以及实盘期权的张数
（`ms_option_purchase`）。实盘决策现在收到场所费率表（`AccountState::fees`，
`ms_strategy_decide` 的 `fees_json`），和回测由同一个 `CompiledStrategy::costs` 解析；
没有费率模型时只禁止新增，平仓照发。

**OKX 实际怎么做，模拟盘实测**（`mayStock` profile，acctLv 3，ETH-USDT-SWAP 逐仓 3 倍，VIP1 吃单 0.045%）：

| 单子 | 保证金 + 开仓费 相对 `availBal` | 结果 |
|---|---|---|
| 限价卖（挂远，不成交），保证金 = 可用 | 多 87.94 | 51008 拒单 |
| 同上，恰好等于 `max-size` | 少 0.35 | 接受；挂单期间冻结 = 保证金 65 064.81 + 吃单费 87.84 |
| `max-size` + 0.01 张 | 多 0.53 | 51008 拒单 |
| 市价买，按标记价保证金 = 可用 | 比 `maxBuy` 多 1.14% | 51008 |
| 市价买，按标记价含费 = 可用 | 比 `maxBuy` 多 1.00% | 51008 |
| 市价买，`maxBuy` × 1.003 / × 1.006 | — | 51008 |
| 市价买，`maxBuy` 再少 0.1% | — | 成交，持仓保证金按成交均价记 |
| 市价卖，按标记价含费再少 0.1% | — | 成交 |

结论：**超出就拒（51008），从不缩量，边界精确到分**；开仓费按吃单费率预留（即便是挂单），
平仓费不预留。保证金的计价价格：限价买按委托价，限价卖按 max(委托价, 标记价)，
**市价买按买方限价（`price-limit` 的 `buyLmt`，当时比标记价高 1.00%）**，市价卖按标记价。
`GET /api/v5/account/max-size` 的 `maxBuy`/`maxSell` 与
`availBal / (价格 × 面值 × (1/杠杆 + 吃单费率))` 逐张吻合（三轮，误差来自读数间的价格跳动）。
所以按决策价算的含费上限对市价卖够用，对市价买还差一个限价带：分配资金恰好等于可用余额时，
满仓市价买仍会被拒。

**开仓单按交易所自己的上限缩量**（May 10-09 定）。运行器发一张新增敞口的单之前读
`account/max-size`（内核 `Read::MaxOrderSize`，按这张单真正发出的 `tdMode` 问——腿先按 §3.24 核对好、杠杆先设成清单的，再问；没有默认值）：
超出就缩到上限的 99.9% 再按最小下单单位取整，日志和状态行写明「交易所当前最多可开多少、
按上限下多少、定仓多少」；连最小一单都开不了就不下并说明；场所说不了（嘉信）或读不到时按定仓原样下，
读不到要记日志。平仓、减仓（包括现货卖出所持）从不缩，也不去问；对冲模式反手只对开仓腿问；
净持仓模式一张单先平后开时上限对它没有测过，不缩，记日志。什么算「新增」只有内核
`guard::opening_base` 一个定义（`ms_opening_base`），运行器原来自己算的 `reduces` 也改用它。

留 0.1% 是因为上限是读的那一刻按买方限价算的，订单到达时按那时的限价判。模拟盘每半秒采一次、
采 90 秒：ETH、BTC 永续的买方限价 1 秒内最多上移 0.014%，5 秒内 0.023%。更快的行情会被拒，
下一根 K 线重新决策。上限能覆盖的不只是限价带，还有手动仓位、别的策略、账户真实费率档占掉的余额。
现货的 `maxBuy` 是空闲计价币 / 最新价（只读核对过，没有限价带也不扣费），在含费定仓下不会撞上。
自检：`maystock-e2e close-doctor` 在两个环境各读一次 BTC-USDT-SWAP 的上限。

**同一形状的另外三个入口，一起堵上：**

- **期权**：权利金预算按权利金单独换算张数，手续费另付——整笔资金买入、到期作废后现金 −1 250
  （权利金 12.5% 的手续费封顶）。现在张数让权利金加手续费装进预算；实盘按交易所冻结权利金的
  限价算，而不是卖一。
- **连续引擎拿浮盈加逐仓保证金**：逐仓仓位的浮盈不是现金，交易所不借给它，强平按均价从已实现
  资金里拿走保证金。按含浮盈的标记权益加仓，10 倍、1 万本金上涨中加仓再跳空，期末 −18 606。
  现在逐仓加仓的占用 = 均价下的保证金 + 浮盈（等价于只能用已实现资金），Reg T 这类按市值放贷的
  不受此限。
- **连续引擎按下一根开盘价定数量、按本根收盘价标记权益**：跳空时两个价位不一致，逐仓仓位把自己的
  亏损读成了加仓空间。现在按决策那根收盘价、对着在那里标记的权益定仓（与 `decide_live` 一致），
  成交时再按成交价重新标记、用同一条规则复核。

顺带修掉一个回测与实盘的分歧：连续回测量「当前敞口」时没除以杠杆，杠杆 > 1 时一个已在目标上的
仓位被看成偏离 `杠杆` 倍，几乎每根都调仓——2 倍、200 根测出 94 笔减仓。敞口现在只有一个定义
（`sizing::exposure_of`），回测和实盘共用。实盘里新方向无法定仓的反手（缺止损距离、没有费率模型）
原来什么都不做，留着信号已经反过来的仓位；回测是先平后定仓的，现在实盘也先平掉。

**护栏走声明。** 测试遍历 `InstrumentType::ALL` 的每个整数杠杆、每种定仓模式、多空两侧和几种
形状不同的费率表，断言占用不超过资金、且被削的单恰好削到上限；三个回测引擎各有一个满仓走最坏
离场的遍历（逐仓强平、全额价格归零、Reg T 盘中追保、期权到期作废），期末不低于零。每条都在
旧逻辑下跑过一次，确认会失败。

**代价。** 连续引擎只在偏离已到阈值时才求上限（上限只会把目标拉近持仓，不到阈值的偏离截断后
更不到）。最坏情况——10 倍满敞口、几乎每根都想加仓——20 万根 1m：111 ms（每根二分）→ 9.4 ms；
完全不设上限是 5.5 ms。秒表：`cargo test --release -- --ignored --nocapture full_exposure_throughput`。

**金标。** 七个满仓用例的终值随仓位缩小约千分之一而移动，交易笔数与离场原因分布一个没变；
`atrRiskSizing` 按风险定仓，没有动。

## 3.24 实盘按回测的保证金下单：模式与杠杆（2026-10-09）

**问题，实测。** 回测按逐仓建模永续（`InstrumentType::margin_regime` → `Isolated`，
强平正好亏光 `名义 / 杠杆` 的保证金），定仓按清单杠杆算（`sizing::target_notional`）。
实盘却两样都没给：runner 的永续单不写 `tdMode`，`wire` 默认填 `cross`；杠杆从来不设也不核对，
OKX 按账户里这条腿当时的杠杆收保证金。模拟盘 ETH-USDT-SWAP 是 3x：一个 10x 清单按 3 万资金定仓，
交易所要 10 万保证金——拒单（51008），账户大一些就悄悄多占 3.3 倍。反过来腿比清单高，
强平线比回测近得多：实盘 ETH 逐仓腿是 10x，而库里的永续策略都是 1x。

**May 的决定**（AskUserQuestion，四项都选推荐）：策略永续用**逐仓**；杠杆不一致时**只在这条腿空着时自动设**，
有仓位就拒绝开仓、绝不改动现有仓位的保证金；腿上有**不是策略开的仓位**就拒绝开仓（逐仓下同合约同方向在 OKX 是同一笔仓位，
一个杠杆、一个强平价，App 里「全平」会连策略那部分一起平）；`maystock://order` 的永续单**一起改**。

**两条规则，各写一处**（`trade::margin`）。开仓单的模式由保证金制度决定：`Isolated` → `isolated`，
和回测强平读的是同一份声明；全额支付的持有（现货、买入的期权）按账户等级定。作用于持仓的单用这笔仓位自己的 `mgnMode`
（平仓面板早就这么做，现在 runner 的平仓、减仓、补挂止损和 URL 下单都走它）。账户等级表每格都是实测：

| acctLv | 现货 | 期权 | 依据 |
|---|---|---|---|
| 1 简单 | cash | cash | 唯一的模式 |
| 2 单币种保证金（实盘） | cash | isolated | 09-18 实盘 ETH-USDT 用 cash 成交；同晚期权 isolated 成交 |
| 3 跨币种保证金（模拟盘） | cross | cross | 10-09 模拟盘现货 cash 被拒 `51000 Parameter tdMode error`，cross 成交 |
| 4 组合保证金 | cross | cross | OKX 文档，未实测（两个账户都不是 4 级） |

账户等级读不到时不猜，拒绝并说明。`wire` 不再给任何品种默认 `tdMode`，没写就在发出前拒绝——
漏掉哪个入口都会当场暴露，而不是悄悄按全仓。runner 的账户配置缓存按模拟盘 / 实盘分开：
原来共用一份，切账户后一小时内会拿模拟盘的 3 级去给实盘的 2 级定模式，现货会变成现货杠杆。

**一条腿**（`trade::leg`）是合约 × 保证金模式 × 方向。开仓或加仓前内核读这条腿的持仓和杠杆：

- 交易所这条腿比台账多出来的是别人的仓位 → `foreignPosition`，不开；比台账少 → `bookAhead`
  （还没对上账的平仓，或者用别的模式开的），不加。差额小于半个最小单位算舍入。
- 杠杆等于清单 → 就绪；不等且腿空着 → `set-leverage` 设成清单的，**设完读回来**确认；不等且有仓位 → `heldAtOtherLeverage`，不开。
- 减仓从不被这条腿拦：只要能定出模式就发；读不到持仓时按策略的模式发并写明。台账有、但交易所在另一个模式里的仓位
  （改之前按全仓开的，比如模拟盘那 0.01 张 BTC 空单）按它自己的模式平。
- 被拦的开仓写进策略状态，原因变了才记日志，同一根 K 线的下一轮重新核对——腿在 K 线中途空出来，就在这根 K 线成交。
  本地拦下（实盘锁、key 不对）和交易所拒单一样，是这根 K 线的终局。
- 顺序是**先核对腿、再按交易所上限缩量（§3.23）、再下单**：`max-size` 按这条腿当时的杠杆和这张单的模式算，
  先问再设杠杆，问到的就是另一个杠杆下的上限。

**OKX 的杠杆只到 0.01，而且会说谎。** `set-leverage` 发 `2.336`，回执原样写 `2.336`，读回来是 `2.33`；`2.005` 读回是 `2`
（模拟盘实测，截断不是四舍五入）。所以设完必须读回，回执不算数；清单杠杆必须在 0.01 档上（`strategy::LEVERAGE_STEP`，
编译期拒绝，`wire` 同样拒绝），不然实盘持有的就不是回测的杠杆。两条新路由 `set-leverage`、`leverage-info`
按 OKX 文档都是每用户每 2 秒 20 次（ccxt cost 1）；`Route::ALL` 由穷举测试保证完整，
测试遍历它断言能改账户的路由只在 `/trade/` 和 `/account/set-` 下、`/asset/`（划转提币所在）下没有一条能改账户。

**模拟盘端到端**（`maystock-e2e leverage-demo`，只碰模拟盘，起点那条腿有仓位就不跑）：清单 5x 的永续策略走一轮 runner，
空腿 100x → 5x（日志写明），成交逐仓 5x、1.2 张，保证金 59.87 = 名义 299.37 ÷ 5；持仓中要 10x 被拒、杠杆仍是 5x；
不并进不属于台账的仓位；runner 按逐仓平掉；现货在 3 级用 cross 成交；最后把杠杆设回起点。
自检本身也守同一条规则：腿空了才恢复杠杆。第一次跑的版本在台账没记上成交时就去恢复，把持仓中的腿从 5x 改成了 100x——
OKX 照做了（保证金被挪走），这正是 runner 绝不做的事；已改成先平仓、腿空了再恢复。

## 3.25 「两根之间几根」从无符号算起（2026-10-09）

§3.21 的 `every_engine_books_exactly_what_it_pays` 在 debug 下 panic 在 `quality.rs` 的
`gaps +=`：它拿小时线跑仓库里的每一份清单，4H、1D 的清单下相邻两根相隔不到一个周期。
连续日历的 `opens_strictly_between` 用 `i64` 算「跨过的整根数减一」，而 `i64::saturating_sub`
饱和在 `i64::MIN`、不在 0——不到一个周期就是 −1，`as usize` 把它变成 `usize::MAX`。
debug 检查溢出所以 panic；App 链接的 release 不检查，按 2^64 回绕：每有这样一对，缺口总数
少 1，这样的对多过真缺口时总数绕过零——1 200 根小时线按 4H 判，实测报「缺失
18446744073709550417 根 K 线」并拒绝序列。这条测试在 release 下实测是能过的，所以没暴露。
实盘没有因此停过：`engine-log.txt` 从 08-12 起没有一条 `stood down`；少算缺口的那种情形不留痕迹。

**计数在无符号域里算。** 两个连续日历分支（`opens_between`、`opens_strictly_between`）
改从 `abs_diff` 得到的 `u64` 跨度算起，饱和减到 0 为止，没有符号可丢。按类型查了内核里
全部有符号转无符号（`clippy::cast_sign_loss`）：除这两处外，`i64 → usize` 四处都是参数、
守卫就在转换旁边；`f64 → usize` 七处是饱和转换，负数得 0 不回绕；`i32 → u32` 两处是复活节公式。

**护栏遍历声明。** `MarketCalendar::ALL` × `strategy::BAR_INTERVALS`——`bar_seconds` 读的就是
这张表，新加的周期当天就被覆盖；新加的日历不进 `ALL`，那条穷举匹配编译不过（同 `ExitReason::ALL`）。
日历层：从周五开盘跨夏令时周末、从独立日前提前收盘日的开盘跨假日，每个预期开盘点与其后
1 ms、半根、差 1 ms 的时刻之间都没有开盘；质量层：比周期细的序列 0 缺口。
在旧算术上这两条分别报 `usize::MAX ≠ 0` 和同一个溢出 panic。

## 3.26 美股的「两个时刻之间几根」数的是会话网格（2026-10-09）

§3.20 说「10:05 进场、15:00 那根判断是五根」，这只在连续市场成立。美股日历的 `opens_between`
从 `from` 本身开始步进 `next_open`，而盘中一个不在网格上的时刻，`next_open` 给的是
「它加一根」而不是下一个网格点——网格被挪到成交时刻上，最后一根数丢了。实测 1H：
10:30:05 成交、15:30 那根判断，数出 4（网格 5）；10:05 成交数出 5（网格 6）；日线
（00:00 戳）周一 09:30:05 成交、周三那根判断，数出 1（网格 2）。成交几乎总在开盘后几秒，
所以实盘的持仓根数（最短持仓、时间屏障、移动止损的锚定窗口）和冷却期在美股上几乎每一笔
都比回测少一根。

**数的是日历自己的网格在 `(from, to]` 里的开盘点。** 日内是 09:30 加整数根、早于收盘，
与 `from` 无关；日线没有声明的钟点（「行情源打什么时间戳就是什么」），取 `to` 的钟点、
每个交易日一根；周线是日历时间，和连续市场共用「从 `to` 往回数」（`opens_back_from`，一处）。
按天做算术，不逐根步进：1m 线的 30 天窗口从约八千步（每根一步）变成约三十步（每天一步）。窗口定长
（`KernelCalendar.barCount(days:)`）传的 `to` 是此刻而不是某根 bar 的开盘，日内网格对任何
时刻都成立，日线取此刻的钟点。Swift 侧的既有期望（周五最后一根到周一开盘 1 根、
30 天窗口 124 根）不变。

**没改的三个。** `next_open`、`opens_strictly_between`、`bars_behind` 仍按前一根步进：
它们判断的是观测到的 bar，一个跑在日历不描述的网格上的行情源（整点对齐的小时线）应当
报 `offGrid`，而不是每两根之间都判出一个洞——吸附到会话网格会把这样的行情源整个拒掉。

**护栏是蛮力对照。** `MarketCalendar::ALL` × `BAR_INTERVALS`，在夏令时周末、独立日前的
提前收盘与假日、感恩节与其后的提前收盘三段里，用 `next_open` 从开盘点一步步走出网格
（与按天算术互相独立），`from` 取网格点前 1 ms、正点、开盘后 5 秒、半根处，以及每天的
零点、盘前、开盘后 5 秒、午间、收盘、盘后、最后一秒（周末假日都算），`to` 取网格点和
任意时刻。旧步进上第一个反例：1m、09:30:05 → 14:55，数出 324，网格 325。

## 4.1 迁移已完成，Swift 侧没有第二份实现

已删除：`Indicators.swift`、`StrategyExpression.swift`、`StrategyEvaluator.swift`、
`ContinuousExposure.swift`，以及 `BacktestEngine` 的整个循环和 `BacktestMetrics` 的统计计算。

保留的是**类型**不是**算法**：`BacktestResult` / `BacktestTrade` / `BacktestMetrics`
仍是 Swift 值类型（界面代码大量使用），但它们的数值全部来自内核。
`BacktestEngine` 缩成一个 60 行的门面，`CompiledStrategy` 只持有清单 + 内核句柄。

两个刻意的例外，都不是引擎逻辑：

- `Statistics`（均值/标准差/下行标准差）—— 相关性、IC、因子回归用的通用统计量，
  不是回测报告的绩效指标。绩效指标只有内核一份。
- `ForesightAnalysis`（波段识别、完美预知上限、水位可靠性）—— 全代码库唯一刻意
  使用未来函数的研究工具，不是交易引擎，不参与任何下单决策。
- `StrategyManifest.marketSeriesNames` —— 只用来阻止 `data` 块跟内置行情变量重名，
  是清单层的策略而非求值逻辑。

`maystock-lab` 的 `--transform`（diff / roc:N / z:N）改成用内核 DSL 表达式求值，
所以 `roc` 和 `stdev` 在研究工具里和在策略清单里是同一个东西。

## 5. 验证：从差分改成黄金数据

删掉任何 Swift 计算代码之前，先证明两边算出同一个结果。18 个差分测试当时全绿：

- 28 条指标/表达式逐根比对（含 Kleene 三值逻辑的判定用例）
- 8 组完整回测**逐笔**比对：均线交叉、止损+止盈同根、移动止损、ATR 风险定仓、
  日内熔断、冷却与最短持仓、永续做空+杠杆、连续敞口波动率目标
- 每笔比方向、成交价、数量、净盈亏、持仓根数、离场原因
- 再比总权益、净值曲线长度、夏普、索提诺、回撤、胜率、期望、费用、暴露度
- 容差 1e-9（指标）/ 1e-6（金额），只留浮点累积误差的余地

Swift 引擎删除后，差分测试失去了对照物，于是改成
[KernelGoldenTests.swift](../Tests/MayStockKitTests/KernelGoldenTests.swift)：
把当时两边一致的那组数值冻结成黄金值（8 个场景 × 成交数/终值/收益/回撤/胜率/手续费）。
之后任何改动内核的编辑，只要挪动了一笔成交、一个成交价或一项指标，就必须**显式**改这些数字 ——
这正是无声数值漂移需要的那个复核时刻。重新生成用
`MAYSTOCK_PRINT_GOLDENS=1 swift test --filter KernelGolden`。

**移植过程中真的被抓到四个差异**（都已修）：

1. `wma` 的 `x[i - period + 1 + k]` —— Swift 用有符号 `Int` 算中间值没问题，
   Rust 的 `usize` 在 `i - period` 这一步就下溢 panic。
2. 内核最初只在编译期检查标识符，未知函数/非法周期要到求值时才报错，
   比 Swift 宽松。用第 4 节的试跑修掉了。
3. 那个试跑一开始用空的外部序列表，于是合法引用 `funding_rate` 的清单
   会被自己的探针判成「未知变量」。改成把已声明的序列填进探针。
4. 现货清单声明做空时，内核的通用拒绝信息盖掉了 Swift 更精确的
   `shortingRequiresSwap`。把市场策略检查移到内核编译之前。

这个坑在本次重构里真的踩到过一次。
